# New Feature Requirements (NEW-01 to NEW-07)

These are proposed requirements, not confirmed bugs. Source locations below were inspected in the current worktrees. Live database schema, deployed policies, secrets, and staging configuration remain unverified unless explicitly stated. **Status vocabulary:** Not Started, Investigating, In Progress, Blocked, Completed. NEW-02 is **In Progress**; the other six requirements remain at investigation/planning stage. No other feature requirement has been implemented.

## NEW-01 — Materials used display

- **Current implementation:** Homeowner `src/pages/DesignerProfile.jsx` parses project `room_materials`; the project gallery converts arrays to `join(", ")` and renders one inline string under “Materials Used”.
- **Affected files/components:** Homeowner `src/pages/DesignerProfile.jsx`, project gallery/material block (around lines 149–199 and 255–265); designer entry/edit form is in designer `src/pages/DesignerDashboard.jsx` (`roomMaterials`, room project editing). Data contract is `designer_projects.room_materials`, potentially JSON object keyed by room.
- **Database / authorization:** No checked-in base schema is available. Existing gallery reads public approved project data through profile queries; retain those visibility rules. No schema change is expected if stored values are already arrays.
- **Reproduction:** Open a public designer profile with a project room whose `room_materials` contains an array of material names.
- **Expected:** Render each material as its own accessible list item, preserving room context and supporting legacy string values safely.
- **Acceptance criteria:** Arrays appear as one item per material; no comma-joined display; empty/invalid values do not create empty bullets or throw; responsive layout and existing public-project visibility remain unchanged.
- **Regression risks:** String and JSON legacy values, whitespace/empty arrays, gallery modal sizing, screen-reader semantics.
- **Required tests:** Component tests for array, legacy string, empty and invalid values; visual/manual narrow viewport review.
- **Status:** Investigating.

## NEW-02 — Designer dashboard navigation and access

- **Current implementation:** `src/utils/designerApproval.js` derives explicit states. A designer row is complete only when the existing dashboard fields `projects_completed` and nonblank `about_text` are present. A signup whose `users.role` is already `designer` but has no application/profile row routes to `/onboarding`; pending application status takes precedence and routes to `/waitlist`; incomplete designer rows route to `/profile`; approved-but-unverified and unknown non-approved statuses remain restricted; dashboard access requires the exact verified flag and the existing application approval condition. `/profile` now selects an owner-scoped completion form for incomplete designer rows and keeps the existing account settings page for other states. UnifiedOnboarding no longer rejects a new signup solely because its role is `designer`. Waitlist polling checks both verification and application status before navigating. Public routes `/aboutcontact`, `/faqs`, and compatibility alias `/faq` remain available. Navbar desktop/mobile links remain on those existing routes.
- **Affected files/components:** Designer `src/utils/designerApproval.js`, `src/components/AuthRoutes.jsx`, `src/App.jsx`, `src/components/Navbar.jsx`, `src/pages/Waitlist.jsx`, `src/pages/UnifiedOnboarding.jsx`, new `src/pages/ProfileRoute.jsx` and `src/pages/DesignerProfileCompletion.jsx`; `src/__tests__/approval.test.jsx`, new `designerAccess.test.jsx`, `profileRoute.test.jsx`, `profileCompletion.test.jsx`, `unifiedOnboarding.test.jsx`, `appRoutes.test.jsx`, `waitlistNavigation.test.jsx`, and updated `integration.test.jsx`.
- **Database / authorization:** No schema, RLS, Edge Function or homeowner app change. Completion writes only `designers` fields for the authenticated `user_id`, then uses existing routing/approval guards. The frontend still requires `designer.is_verified === true` and, when present, application status `approved`. Staging RLS behavior for the profile update was not verified; frontend guards are not a replacement for backend authorization.
- **Reproduction:** Test a newly registered designer with no application, a designer row missing required profile fields, and a submitted application with pending status. Navigate dashboard, Profile, Contact Us, FAQs, direct routes, and refresh.
- **Expected:** Each state has a reachable next step and permitted support/navigation links. Incomplete users can complete profile; pending users see waitlist/allowed support pages; only approved designers enter the operational dashboard.
- **Acceptance criteria:** State routes avoid loops; Profile selects completion vs account settings appropriately; Contact and FAQ work in desktop/mobile navigation and direct URLs; pending/unverified accounts remain blocked from dashboard; an incomplete user writes only their own designer row.
- **Regression risks:** Guard overlap, completion definition drift, stale auth query cache, direct URL/back navigation, application state and verification polling races.
- **Required tests:** Vitest route matrix, profile form owner-scoped update, support links/routes, browser history, and negative dashboard access; staging RLS authorization check remains required.
- **Status:** In Progress — local implementation and Vitest coverage are complete; staging RLS authorization remains unverified.

## NEW-03 — Inquiry and client contact details

- **Current implementation:** Designer `src/pages/DesignerDashboard.jsx` queries `connections` with `client:users(full_name,email,phone,city)` for the assigned `designer_id`. `LeadCard` displays name and inquiry details in all statuses when expanded, but phone/email are rendered only for `accepted` (Active). Statuses are `pending` (New Request), `accepted` (Active), and `on_hold` (Hold). The card offers accept/hold/delete for pending inquiries.
- **Affected files/components:** Designer `src/pages/DesignerDashboard.jsx` (lead query, `LeadCard`, status handler and tabs); potentially shared query/service in `src/services/projectService.js`; Supabase policies for `connections` and `users`.
- **Database / authorization:** Exact deployed FK/join and RLS cannot be verified from the sole checked-in hardening migration. Need row-scoped read access for the assigned designer to inquiry and only the associated client's necessary contact fields. Do not broaden access to all users or unrelated inquiries. Keep mutation authorization on connection updates separate from client contact reads.
- **Reproduction:** Create/locate an assigned connection in each of pending, on_hold, and accepted status; expand it as assigned designer. Repeat as a different designer and unauthenticated user.
- **Expected:** Assigned designer can review client name, phone, email and full requirements before changing status. Unauthorized designers cannot read the row or contact information.
- **Acceptance criteria:** Contact links and details available across all three statuses; inquiry message/scope/style/budget/timeline preserved; only assigned designer and explicitly authorized service roles can retrieve; cross-designer and anonymous reads denied.
- **Regression risks:** PII exposure through joins, insufficient RLS on joined `users`, null contact values, contact rendering breaking status card layout.
- **Required tests:** UI tests across statuses; RLS integration tests for assigned/unassigned/anonymous roles; query error and missing-contact cases.
- **Status:** Investigating.

## NEW-04 — Admin Manage Workspace permissions

- **Current implementation:** Homeowner `src/App.jsx` protects `/admin` and `/admin/manage-designer/:id` with `RequireAdmin`. AdminDashboard’s Active Designers card navigates “Manage Workspace” to `/admin/manage-designer/${d.id}`. It renders homeowner `src/pages/DesignerDashboard.jsx` in admin override mode, which includes “Inquiries & Clients” and status/delete actions against `connections`, alongside profile, portfolio and settings management. The user request calls this “Manage Workspace”; source labels the section “Inquiries & Clients”.
- **Affected files/components:** Homeowner `src/App.jsx`, `src/components/AuthRoutes.jsx`, `src/pages/AdminDashboard.jsx` (Manage Workspace entry), `src/pages/DesignerDashboard.jsx` (admin override and inquiry mutations), and deployed RLS/service backend.
- **Database / authorization:** Inspect `connections` update/delete policies and admin helper before implementation. Smallest safe approach is to make this section read-only for admin override, while retaining explicitly intended profile/portfolio workflows, plus ensure policies do not grant an unintended admin mutation path. Do not remove legitimate application review/admin actions elsewhere.
- **Reproduction:** Admin opens an Active Designer’s Manage Workspace, selects an inquiry, attempts Active/Hold/Delete; separately verify existing profile/portfolio admin tasks.
- **Expected:** Admin can inspect workspace as allowed but cannot modify Inquiries & Clients. Designer-assigned workflow remains intact; other explicitly authorized admin features keep working.
- **Acceptance criteria:** No inquiry mutation controls in admin override and requests are denied at the data layer for admin-only caller where no separate authorization exists; designer’s assigned status workflow unchanged; profile and portfolio admin workflows remain available.
- **Regression risks:** Admin override accidentally losing legitimate profile controls, or UI-only restriction leaving direct API mutation possible.
- **Required tests:** Admin override component tests, direct Supabase mutation denial test, regression tests for authorized profile management and designer status updates.
- **Status:** Investigating.

## NEW-05 — Designer Video Management System

- **Current implementation / source discrepancy:** The checked-out designer collaboration form `src/pages/UnifiedOnboarding.jsx` does **not** contain video fields. The two existing fields are `video_link` and `video_link_2` in designer `src/pages/DesignerDashboard.jsx`, in the profile edit form (`renderProfileForm`, used both for incomplete profile completion and Edit Profile). The handler saves both to `designers`. Admin homeowner `src/pages/AdminDashboard.jsx`’s designer detail card displays original links if present, but there is no video-processing workflow/status editor. Public homeowner profile `src/pages/DesignerProfile.jsx` embeds both fields. Thus the requested “collaboration form already contains two fields” does not match current source and must be reconciled against the deployed version/data before implementation.
- **Exact requested discovery:** Existing field names: `video_link`, `video_link_2`. Frontend fields: designer `src/pages/DesignerDashboard.jsx`, `renderProfileForm` (profile completion and Edit Profile; around lines 1229–1233 and 1415–1418). Persisted table/columns as used by code: `designers.video_link`, `designers.video_link_2`. This table/column existence is inferred from live Supabase client calls; the checked-in repository contains no baseline schema migration defining these columns, so database confirmation is **unverified**. Admin-managed profiles: homeowner AdminDashboard’s Active Designers list offers Manage Workspace to `/admin/manage-designer/:id`; homeowner DesignerDashboard checks admin role, loads target `designers` row, and enables profile/portfolio/inquiry tabs in “ADMIN OVERRIDE MODE”. AdminDashboard itself also loads designer data and displays original video links on designer cards/details. Route: homeowner `/admin` and `/admin/manage-designer/:id`, guarded by `RequireAdmin`. Current sidebar: Overview, Requests, Verify Profiles, Active Designers, Onboard VIP, Inbox. Public component: homeowner `src/pages/DesignerProfile.jsx`, Video Showcase. New table/fields: no publication URL/status columns are referenced in checked-in code; adding metadata is likely necessary, but only after live schema inspection confirms absence.
- **Affected files/components:** Designer `src/pages/DesignerDashboard.jsx` (keep both original input fields/workflow); homeowner `src/pages/AdminDashboard.jsx` (new Designers Videos sidebar/workspace and admin actions; existing original-link display); homeowner `src/pages/DesignerProfile.jsx` (show only final published YouTube URL); both apps’ Supabase client selection/types if present; schema migration and RLS; terms/consent UI and versioned consent storage.
- **Database / authorization:** Reuse `designers.video_link` and `designers.video_link_2`; do not duplicate original media fields or require resubmission. Verify deployed table, column types, current grants and policies. If absent, add only necessary publishing metadata, likely `video_status`, `youtube_video_url`, `video_published_at`, `video_updated_at`, with constrained values and timestamps. Admin status/URL writes must be server/policy protected. Public reads should expose only final published URL; original Drive/video links must not be selected through public views or exposed by broad `select('*')`. If column-level control cannot be guaranteed through existing RLS, use a restricted public view/RPC. Store versioned designer consent as a new append-only record (designer, consent version, accepted timestamp, text/hash and withdrawal metadata) or equivalent audited design after schema check; do not silently rewrite existing consent. Consent must cover editing/branding, official-channel publishing, profile embedding, ownership/usage and removal/withdrawal; wording requires legal review before capture.
- **Internal production:** Original downloads, editing with brand, and publishing to the official channel are performed outside the app. App records status and final URL only; no upload/editing/publishing pipeline is required.
- **Reproduction:** Designer saves two existing links; admin opens current profile manager; public profile is loaded. Current app has no status/published-URL management and exposes both stored inputs publicly when valid.
- **Expected:** Admin-only Designers Videos section lists eligible designers, details and original links, statuses Pending/In Editing/Published, and saves final YouTube URL. Public profile shows at most one final branded YouTube intro and hides section absent final URL. Designer continues using the two existing fields and neither resubmits nor loses them.
- **Acceptance criteria:** Both original fields remain unchanged and associated to same designer; only authorized admins can view originals and mutate status/final URL; public/anonymous queries never expose original links; one validated final YouTube URL renders only when published; no external production actions are represented as app functionality; consent is versioned and auditable, with legal approval before launch.
- **Regression risks:** Public leakage through broad profile selects, losing old links during migration, untrusted URL/embed injection, admin route/RLS gaps, overwritten consent history, false “Published” state without final URL.
- **Required tests:** Designer form round-trip; admin-only list/read/write and non-admin denial; URL validation and status transitions; public query serialization/leakage test; one-video/hide-empty tests; migration backfill/no-data-loss test; versioned consent acceptance/withdrawal audit tests.
- **Status:** Investigating.

## NEW-06 — Designer business location and nearby discovery

- **Current implementation:** Homeowner `src/pages/Designers.jsx` has a geolocation search calling `get_designers_nearby(user_lat,user_lng,radius_meters:50000)` with fixed 50 km. No matching RPC is present in checked-in migrations. Designer `src/pages/DesignerDashboard.jsx` collects browser geolocation and writes `users.location` as a point; homeowner `src/pages/UserProfile.jsx` also writes user location. This appears to be user/client location, not a verified business office location. Existing directory code uses designer city. PostGIS extension, deployed columns, RPC definition and RLS are unverified.
- **Affected files/components:** Homeowner `src/pages/Designers.jsx`, nearby filters; designer `src/pages/DesignerDashboard.jsx` location/profile controls; homeowner `src/pages/AdminDashboard.jsx` VIP city form (NEW-07); `users` and `designers` schemas; new migration/RPC and RLS; tests.
- **Database / authorization:** First inspect deployed schema, `users.location` type, PostGIS extension/functions, existing `designers` address columns, grants, RLS and function security mode. Store business location separately from any residential/client location. Proposed data: locality, city, state, PIN code and optionally business coordinates (or a business-location table); radius query should use verified coordinates/geography and return only public designer fields plus computed distance. No residential address should be part of public search output. Do not apply migration to production.
- **Reproduction:** Click Find Designers Near Me in homeowner directory; source sends fixed 50 km RPC; inspect backend function/schema availability. A migration search finds no function/coordinates definitions.
- **Expected:** Homeowners can choose 5, 10, 25 or 50 km around their consented/current position and see eligible public designers with distance; designers can maintain business locality without exposing home address.
- **Acceptance criteria:** Radius options work and are validated; only public/verified/eligible designers returned; location permission denial handled; residential address never returned; city/radius filters compose predictably; indexes and query plan suitable for expected data volume; RLS and RPC execute with least privilege.
- **Regression risks:** Existing `users.location` misuse, incorrect coordinate order/units, geolocation consent, boundary errors, public PII leakage, unavailable PostGIS.
- **Required tests:** RPC distance/radius boundary and invalid inputs; RLS and public-field allowlist tests; migration on disposable staging database; frontend geolocation permission/error and radius selection tests.
- **Status:** Blocked — live database schema, RPC, RLS and PostGIS availability cannot be verified without staging schema access/credentials. No migration is proposed for execution until that evidence is available.

## NEW-07 — VIP onboarding improvements

- **Current implementation:** Homeowner `src/pages/AdminDashboard.jsx` contains `AdminOnboardDesigner` (VIP form) with city but no structured locality/state/PIN/business coordinates, and a “Make Featured” checkbox bound to `featured_status`. Separate featured request/admin workflows remain in AdminDashboard and must not be removed. Designer account creation/registration and profile completion are handled in designer `src/pages/Register.jsx` and `src/pages/DesignerDashboard.jsx`; dashboard already has `renderProfileForm` for incomplete profiles.
- **Affected files/components:** Homeowner `src/pages/AdminDashboard.jsx` (`AdminOnboardDesigner` only); designer `src/pages/Register.jsx`, `src/components/AuthRoutes.jsx`, `src/pages/DesignerDashboard.jsx` profile-completion path; shared/deployed `designers` location schema and provisioning Edge Function contract.
- **Database / authorization:** Reuse verified business-location fields from NEW-06. Preserve current admin-only provisioning and verification rules. Profile completion remains scoped to authenticated owner or admin; do not create a second competing profile flow or grant user-selected verification/featured privileges. Existing feature status and independent admin featured controls remain supported.
- **Reproduction:** Admin opens Onboard VIP; inspect fields and submit; VIP designer signs in and attempts dashboard profile completion. Current form has city only and Make Featured; dashboard has general profile completion UI.
- **Expected:** VIP onboarding collects business locality/city/state/PIN (coordinates only if appropriate), does not offer a featured toggle, and the onboarded designer can complete remaining profile fields in the existing dashboard flow.
- **Acceptance criteria:** VIP form omits only its Make Featured option; backend default for VIP is standard; unrelated featured workflows unchanged; location persists to the agreed business fields; VIP can reach profile-completion UI without bypassing authentication/verification; no duplicate completion flow.
- **Regression risks:** Changing shared `featured_status` semantics, inconsistent onboarding/profile location fields, auto-verification behavior, VIP redirect/access loops.
- **Required tests:** VIP payload default, unrelated featured admin regression, location validation/persistence, new VIP login and incomplete profile route matrix, auth/RLS ownership denial.
- **Status:** Investigating.
